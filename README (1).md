# Arabizi-IR Pilot: Measuring and Repairing Retrieval Degradation for Romanized Arabic (Arabizi) Queries

## 1. Overview

Arabic speakers very frequently type search queries in **Arabizi** (also called Franco-Arabic): Arabic written in Latin letters and digits, for example `2adesh 3adad el abraj el falakiyye?` instead of the Arabic-script form `كم عدد الأبراج الفلكية؟` ("How many zodiac signs are there?"). Standard Arabic retrieval pipelines are built around Arabic-script text, so an Arabizi query shares almost no surface form with the Arabic documents it is meant to find.

This project is a compact, fully reproducible pilot that:

1. **Quantifies** how much retrieval quality collapses when Arabic queries are written in Arabizi, for three retrieval paradigms: lexical (BM25), dense (multilingual-E5) and hybrid (BM25 + dense fused with Reciprocal Rank Fusion).
2. **Repairs** the problem with a lightweight *reverse transliteration* (Arabizi → Arabic) module that is **constrained by a lexicon built from the target corpus itself**, and optionally fuses multiple candidate reconstructions.
3. **Tests** the effect with paired bootstrap confidence intervals and Holm-corrected significance tests, plus ablations and a per-query error analysis.

The experiments use the Arabic portion of the **MIRACL** benchmark and combine **synthetic Arabizi** (three controlled noise levels) with a small **human-written** set of dialectal Arabic and dialectal Arabizi queries.

## 2. Motivation and Practical Value

- **Real user behaviour.** Arabizi is common in chat, social media and mobile search. Search systems that ignore it silently fail for a large group of users.
- **Measured, not assumed.** The pilot gives concrete numbers for how bad the failure is. Raw Arabizi queries retrieve essentially nothing (nDCG@10 ≈ 0) for all three systems.
- **A cheap fix that needs no training data.** The repair module needs no parallel Arabizi–Arabic corpus and no model training. It only needs the document collection that is already being searched, which makes it easy to bolt onto an existing search stack as a query-rewriting step.
- **Separates script from dialect.** The 2×2 design shows whether the difficulty comes from *dialectal wording* or from the *Latin script*. In this pilot it comes almost entirely from the script.
- **A reusable evaluation harness.** The notebook can be re-used to evaluate other transliteration or query-normalization methods (including LLM-based ones, see Section 6.7).

## 4. Experimental Design

A 2×2 design crossing **register** (Modern Standard vs. dialect) and **script** (Arabic vs. Arabizi):

| Condition | Register | Script | Source |
|-----------|----------|--------|--------|
| **Q0** | Standard Arabic | Arabic | Original MIRACL queries (reference upper bound) |
| **Q1** (L1, L2, L3) | Standard Arabic | Arabizi | Synthetically generated at 3 noise levels |
| **Q2** | Dialect | Arabic | Human-written (60 queries) |
| **Q3** | Dialect | Arabizi | Human-written (60 queries) |

**Synthetic noise levels** (`p_digit`, `p_drop_vowel`):
- **L1** (0.0, 0.0): near-regular romanization, no digits, no vowel deletion (close to automatic romanization schemes).
- **L2** (0.5, 0.3): medium noise.
- **L3** (0.9, 0.6): heavy noise, many digit substitutions (`3`, `7`, `5`, `2`, `9`, `6`) and frequent vowel omission.

## 6. Methods

### 6.1 Text normalization
A single normalization function is applied **identically to documents and queries** (inconsistent normalization between index and query side is a known source of degradation): diacritics and tatweel removal, unification of alef variants (`أ إ آ ٱ → ا`), `ى → ي`, `ة → ه`, `ؤ → و`, `ئ → ي`, and lower-casing. Tokenization is a Unicode word-regex.

### 6.2 Retrieval systems
- **BM25:** `rank_bm25` (`BM25Okapi`) over the normalized tokens. Note that this is a simple BM25 implementation, **not** the Lucene Arabic analyzer (no stemming).
- **Dense:** `intfloat/multilingual-e5-small` via `sentence-transformers`, with the `query:` / `passage:` prefixes, max length 256, normalized embeddings and cosine (dot-product) search.
- **Hybrid:** **Reciprocal Rank Fusion** (RRF, `k = 60`, depth 100) of the BM25 and dense rankings.

### 6.3 Synthetic Arabizi generator
A character-level, stochastic Arabic → Arabizi generator. Each Arabic letter has a list of plausible Latin or digit realizations (for example `ع → 3 / a / aa`, `ح → 7 / h`, `خ → 5 / kh`, `ق → q / 2 / 9 / k`). At each noise level it chooses digits versus letters and drops vowels with the level's probabilities. Generation is seeded per query and level for reproducibility.

### 6.4 Lexicon-constrained reverse transliteration (the proposed repair)
1. **Lexicon:** build a vocabulary with frequencies, and a prefix-frequency table, from the (normalized) target corpus.
2. **Segmentation:** split each Arabizi token into units (digraphs such as `sh`, `kh`, `gh`, `th`, `aa`, `ee`, `oo`, and single characters or digits).
3. **Expansion with pruning:** expand each unit with its possible Arabic letters (`DEROM` table, hand-written and intentionally separate from the generator table) using **beam search**. At every step, partial hypotheses that are **not a prefix of any corpus word** are discarded. This is what makes the search tractable and keeps the output linguistically valid.
4. **Ranking:** surviving full words must exist in the corpus vocabulary and are ranked by corpus frequency; the top-*k* are returned.
5. **Special handling:** a detached definite article (`el`, `al`, `il`, `l`) is attached to the following word as `ال`. Unknown tokens are left unchanged.
6. **Query-level candidates:** the *j*-th query candidate combines the *j*-th candidate of every word (a deliberately crude strategy for the pilot).

### 6.5 Repair strategies compared
| Code | Strategy |
|------|----------|
| `raw` | No repair; the Arabizi query is searched as is. |
| `R1` | Search with the single best reconstructed query. |
| `R3` | Search with *k* = 5 candidate queries and fuse the rankings with RRF. |
| `R4` | `R3` plus the raw query as an additional run. |

### 6.6 Evaluation and statistics
- **Metric:** nDCG@10 per query (binary relevance).
- **Gap recovered:** `(nDCG_repaired − nDCG_raw) / (nDCG_Q0 − nDCG_raw)`, i.e. the fraction of the lost effectiveness that the repair brings back.
- **Significance:** paired bootstrap (10,000 resamples) for mean differences with 95% confidence intervals and two-sided p-values, with **Holm** correction across all tests.
- **Ablations:** number of candidates *k* ∈ {1, 3, 5, 10}, and removal of the lexicon constraint.
- **Error analysis:** the 40 worst cases are exported with an empty `error_type` column for manual labelling (letter ambiguity, vowel omission, out-of-lexicon dialectal word, foreign name, code-mixing, other).

### 6.7 Optional: LLM-based candidates
The notebook defines `llm_candidates(q, llm_fn, k)`, a hook for plugging any LLM (open model or API) into the candidate list. It is **not evaluated in the reported results**. If used, a model different from the one that produced the data should be chosen, and its name, version and date recorded.

## 8. Key Findings (Pilot)

**Table 1. nDCG@10 by condition.** "Best repair" is the best of R1/R3/R4 for that cell. Q0 is computed on the same queries as the condition it is compared with.

| Condition (n) | Version | BM25 | mE5-small | Hybrid |
|---------------|---------|------|-----------|--------|
| Q0, standard Arabic (200) | reference | 0.621 | 0.852 | 0.772 |
| Q1-L1 (200) | raw | 0.002 | 0.000 | 0.000 |
| | best repair | 0.364 (R3) | 0.296 (R1) | 0.412 (R1) |
| Q1-L2 (200) | raw | 0.002 | 0.000 | 0.000 |
| | best repair | 0.188 (R1) | 0.169 (R1) | 0.237 (R1) |
| Q1-L3 (200) | raw | 0.002 | 0.000 | 0.000 |
| | best repair | 0.110 (R1) | 0.116 (R1) | 0.153 (R1) |
| Q2, dialect Arabic (60) | raw | 0.581 | 0.832 | 0.759 |
| | Q0 on same queries | 0.577 | 0.867 | 0.758 |
| Q3, dialect Arabizi (60) | raw | 0.010 | 0.027 | 0.037 |
| | best repair | 0.345 (R1) | 0.129 (R1) | 0.339 (R1) |
| | Q0 on same queries | 0.577 | 0.867 | 0.758 |

**Table 2. Repair strategies on human-written Arabizi (Q3, n = 60), nDCG@10.**

| System | raw | R1 | R3 | R4 | Gap recovered by R1 |
|--------|-----|----|----|----|---------------------|
| BM25 | 0.010 | **0.345** | 0.212 | 0.219 | 59% |
| mE5-small | 0.027 | **0.129** | 0.025 | 0.027 | 12% |
| Hybrid | 0.037 | **0.339** | 0.138 | 0.127 | 42% |

**Main observations**

1. **Raw Arabizi breaks all three systems.** nDCG@10 drops from 0.62 / 0.85 / 0.77 to nearly zero. The dense multilingual model offers no protection against Latin-script Arabic.
2. **The script, not the dialect, is the bottleneck.** Dialectal Arabic written in Arabic script (Q2) performs about as well as Standard Arabic for BM25 and hybrid, with a small drop for the dense model (−0.035), whereas the same dialect in Arabizi (Q3) collapses.
3. **Degradation increases with noise.** Even after repair, the best hybrid score falls from 0.412 (L1) to 0.237 (L2) to 0.153 (L3).
4. **Lexicon-constrained reverse transliteration recovers a large share of the loss for BM25 and hybrid.** On human Arabizi, a single repaired query lifts BM25 from 0.010 to 0.345 and hybrid from 0.037 to 0.339 (all differences significant after Holm correction). The dense model benefits much less.
5. **The lexicon constraint is essential.** Removing it roughly halves or worsens the result (for example, Q3 hybrid with R3, k = 5: 0.138 with the lexicon vs. 0.009 without; Q1-L2 BM25: 0.186 vs. 0.080).
6. **More candidates did not help in this pilot.** The single top candidate (R1) was generally best, and adding candidates through RRF lowered effectiveness, especially on human Arabizi (BM25, Q3: k = 1 → 0.345, k = 3 → 0.251, k = 5 → 0.212, k = 10 → 0.207). A plausible explanation, which this pilot did not test, is that the column-wise combination of per-word candidates produces incoherent lower-ranked queries that add noise to the fusion. For the dense model, R3 and R4 gave no significant gain on Q3 (Holm-adjusted p = 1.0).
7. **Per-query effect (Q3, hybrid, R3 vs. raw):** 15 queries improved, 4 got worse, 41 were unchanged. The exported error sample shows many Arabizi words that remain unresolved (left in Latin script) after repair.

## 9. Limitations

- **Small scale:** 200 queries; a down-sampled corpus (about 32K passages); only 60 human-written queries, written by the project author, so results may not generalize to other dialects or writers.
- **Simple BM25:** `rank_bm25` without the Lucene Arabic analyzer or stemming; a small dense model (mE5-small), no fine-tuning, no re-ranker.
- **Circularity risk:** the synthetic generator and the reverse transliterator encode similar romanization conventions, even though their tables were written separately. The human set is the unbiased test.
- **Crude candidate construction:** pairing the *j*-th candidate of each word ignores word interactions, so the weak results of multi-candidate fusion should not be read as a limit of fusion in general.
- **Pilot status:** no hyper-parameter search, a single random seed, and only one lexicon-based method evaluated. The LLM-based variant is implemented as a hook but not evaluated.
- **Absolute scores are not comparable** with published MIRACL numbers (see Section 5).

## 11. Future Work

- Larger and more diverse human-written Arabizi sets covering several dialects and several writers.
- Better candidate construction (word-level lattice or joint decoding with a language model) instead of the column-wise combination.
- Evaluating LLM-generated candidates against the lexicon-constrained method.
- Stronger baselines: Lucene Arabic analyzer, larger multilingual dense models, re-rankers, and the full MIRACL corpus.
- Handling of code-mixing and foreign named entities.
